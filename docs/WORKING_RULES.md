# Working rules — how a coordinator, a builder and the lenses work together

These are the operating rules that run alongside the verification harness (`SOLIDITY_VERIFICATION_HARNESS.md`). The harness says what must be proven; this file says how the seats work day to day so the proof happens without waste. They were distilled from a real build (Up Only, Sep 2026) and are binding on every project created from this template. Copy them into the project's `CLAUDE.md` or link this file from it.

## The ladder
- **Harness:** what an agent can do (its tools, its sandbox, the wrappers that refuse).
- **Loop:** what is true (checks that can fail, run by script, before a lens is spent).
- **Graph:** what happens next and who decides (lanes, merge tiers, the owner's gates).
Every rule below sits on one layer, and a lesson is filed on the layer that owns it (rule 38).

## 1. Merges and PRs
1. **Merges are gated by what a mistake costs to undo, decided by a script from what changed, failing closed.** The owner's attention goes where one revert cannot undo the damage; where one revert can, a recorded non-author lens is enough. (Owner decision, 2026-11; it replaces "no agent merges a PR, ever".) Builders, checkers and lanes never merge at any tier; only the coordinator merges tier 1, and only through the gate.
   - **Tier 1, one-step revert:** docs, evidence and records, and other demonstrably inert artifacts (property k); UI code only where a parser proves the diff presentation-only; in a contract repo, `script/`, `test/`, `tools/` and docs, with no `src/` change. The coordinator merges after a passing non-author lens on the exact head. In a contract repo it merges into the integration branch, never into `main`, and tells the owner in one line afterwards.
   - **Tier 2, cleanup undo:** `main`; gate files (`.github/`, CI scripts, scan config, analyzer waiver databases, census manifests); agent instruction files. The owner merges.
   - **Tier 3, no undo:** contract source, deploy, multisig writes, secrets, repository settings. The owner merges, after the security gate.
   - **A tier is priced by what the change can reach after it lands.** Landing on a branch and promotion to anything a user or a chain can see (a live site, a deploy, a multisig write) are separate gates, and promotion is always the higher tier: a harmless-looking path still reaches users once it is promoted.

   Every tier gate has these properties, each for its reason. (2026-11: the first tier script merged one change before any lens had read it. An automated review of its four successive versions found twelve holes; a non-author lens then ran one hundred inputs against the fourth and found twenty more root causes, and ruled that a deny-list of names and text patterns over code cannot be made sound by extending it.)
   - a. **No gate is relied on before a non-author lens has read it.** A tier gate is itself a consequence path.
   - b. **It decides from changed paths and added content, never from a model's label, and any parse or read failure fails closed to the owner's tier.** A label is a claim; a path and a parsed file are facts.
   - c. **Renames and deletions are judged on both the old and the new path.** Otherwise a move launders an owner-tier file into a tier-1 folder.
   - d. **Agent instruction files, CI files, the gate's own files and anything the gate reads are always the owner's tier.** A change to the gate can never judge itself.
   - e. **It runs from an untracked, checksum-pinned copy outside every repository, with its parser installed beside it,** never from a tracked path or a checkout's dependencies. A PR that edits the gate would otherwise write its own verdict.
   - f. **Content checks use a real parser for the language, not regular expressions over a patch, and compare items one by one, never by count.** A regular expression misses a name added inside an existing multi-line import, and a count lets a swap pass as no change.
   - g. **The merge is pinned to the exact head the gate judged** (the host's match-head option) **and needs a recorded non-author PASS on that same head and a clean merge state.** A push after the verdict cannot ride through.
   - h. **The lens verdict the gate needs is one the merging seat cannot mint.** Tamper-evident, usable now: the gate reads the lens tool's own session record by its id, never a pass file the coordinator wrote, and records that record's digest, its sandbox mode and the exact head it names. Structural: the lens posts a commit status or review on the exact head under a machine identity whose credential the coordinator session does not hold, and the branch ruleset requires that status. On one machine under one user only the structural form is a wall; the tamper-evident form stops a careless seat and leaves a dishonest one a mismatched trail.
   - i. **A local text-matching hook is not the wall.** It cannot see a merge performed inside a script. The wall is the host: a separate machine identity for agents, a required owner review on owner-tier paths and a required lens status (README, day-one setup). The owner's guard hook is defence in depth, and it names the one permitted merge path by absolute path and checksum, an exception the owner writes.
   - j. **One implementation, with each project's path lists as data.** Two diverging tier scripts is the failure. Its planned home is `tools/tier/` in this repository (the engine, a per-project data file, content screens keyed by language), to be added by a separate PR after both lenses; until it lands, each project's gate meets a-i and k-m. The reference implementation is a coordinator's `pr-tier.py`, `pr-tier-imports.cjs` and `merge-tier1.sh` (2026-11): copy the properties, never its path lists.
   - k. **Tier 1 is an allow-list of demonstrably inert artifacts, never a deny-list over code.** Inert means a regular, non-executable file of an approved kind that the application, the build, CI and the tooling cannot execute or read as active configuration; a folder name (docs, logs, tests) never makes a script, a query file or a config inert. Code changes go to the owner's tier unless a conservative parser-based verifier positively proves a narrowly defined harmless diff (for UI, presentation-only), and stylesheets go with code until they have a verifier of their own. Unknown goes to the owner. A deny-list loses to the next spelling of the same effect.
   - l. **The gate judges validated git objects, and any failure to obtain them is an error, never a pass.** Paths are canonical (no dot segments), and each file's object type and mode are established, so a symlink, a submodule link or an executable bit is seen; the changed-file list is unique, schema-checked, complete and bound to the judged head and base; an empty or missing patch is never complete evidence; a helper's output is ignored when its exit is non-zero; a failed fetch or merge-base stops the gate for every class of change. The base as well as the head is pinned at merge time.
   - m. **The gate's own trust anchors are the owner's.** The pinned checksums of the installed gate, the per-project policy data and the allow-list of merge paths live where the merging seat cannot write them; policy data is schema-validated, versioned and unable to weaken the engine's object, provenance or approval requirements.
2. **A PR opens only after its second lens has passed.** The PR body carries the verdict line: who reviewed, what they found, what was folded. CI green is never the review.
3. **One PR per real change; batch the rest.** Records, reports and hygiene changes accumulate on a staging branch (`docs/next`) and land as one PR.

## 2. Seats
4. **Author ≠ checker.** No seat clears its own work. A builder never approves its own PR; a checker never checks work its own model wrote; a top-severity oracle's lens differs from the builder's.
5. **Fresh thread per builder task; one task per thread.** A mid-task note goes into the live thread through a note script; a new task always respawns. Dispatch through a script that guards against the tool's own dialogs (updates, rate-limit model switches, slow-response menus): a bare Enter has switched models before.
6. **Briefs state reading scope** as exact files and line ranges, never "read in full"; they name the prior report if one exists; they require commit-early, real exit codes and log paths in the hand-back. Files stay under 800 lines; a seat that reads a 2,000-line file whole dies with nothing committed.
7. **Non-interactive lanes for the cheap seats.** Red-team and oracle seats run headless with auto-approval in their own clones and tmux windows, streaming to a log; the owner never approves their commands. The builder keeps manual approvals.

## 3. Discipline
8. **Primary-source discipline.** No claim about an external system without an in-context citation (a doc line, `file:line`, a decoded transaction, an RPC read); otherwise write "UNVERIFIED — not checked". "Probably/should/presumably" are banned as substitutes for looking. Equivalence and absence claims need end-to-end verification, never inference from silence. On pushback, re-read the source first. Tag material claims `[verified: <cite>]` or `[UNVERIFIED]`.
9. **Verify the claim, not its neighbour.** Reading the arithmetic at one line is not reading the guard on its input at another. Bind each proof to the exact property at its exact strength.
10. **Consequence decides the model, for authorship as well as review.** Anything that moves or gates money, authenticates, or protects data gets the strongest model for review, an adversarial second lens from a different model family, a real-world test where one exists (a live-state fork beats a mock; a differential against the live reference beats both), and never self-clearance. Complex tooling (drivers, runners, gate scripts) is a consequence path for its author: the strongest available author writes it, and fast models keep bounded edits and reading lanes (2026-11: a deploy-ceremony driver written by the fastest model came back from its lens with fifteen findings). Work whose error is self-evident and cheap to redo can use cheaper models.
11. **Nothing ratified is re-decided by an executing seat.** If something looks like a product or design call, it is written as a question for the owner to take to the deciding gate, never as a recommendation in a record. Every parameter in a record cites the ruling that set it.
12. **Test against the live reference whenever one exists.** A forked contract carries a live-matrix differential against the original on a pinned fork of mainnet; every difference maps to a named, priced register entry or blocks close-out; the run re-executes at every checkpoint close and every fee-path change, with its run id cited.

## 4. Machinery and spend
13. **New machinery gets two questions before it is built:** is this a rabbit hole, and does it bring us closer to shipping? Prefer re-running an existing check over building a new one. Two HOLDs on the same artifact for new shapes means stop and re-open the design with the owner, never a third round.
14. **Spend is orchestration volume, and the control is planning before dispatch, never a cap.** Task count and context size drive cost, not model choice; never downgrade a verifier to save tokens. Lenses read a verdict and a findings table, never a whole packet; fix loops batch fixes before re-checking. Before every dispatch the coordinator plans: the right seat and author for the item, the exact deliverable and its path, what already exists that must not be redone, and an estimate stated as a number, never as a limit. Never a spend cap, a hard stop on a number, or a reserve held on a meter: a cap that stops a task with nothing committed wastes the spend it was meant to protect (2026-09). Each account's meter is read from the tool's own rate-limit record, never recalled (2026-11: two accounts' quotas were held backwards for hours). Never park work behind a reset while another account has room: every seat with work spends what is left, and a meter at zero waits for its reset while the other account carries on. `SEAT_OPERATIONS.md` §8 states the same budget rule.
15. **Tooling and CI changes are not "working" until their runtime capability is verified at source** (token scopes from the runner's permissions log, tools present on the runner), and their acceptance control is a mechanism-specific log line, never an outcome a silent failure also produces.
16. **A passing gate proves coverage and binding, never truth.** After any gate goes green, adversarially audit the content: does every claim prove its label, does every citation resolve to the exact assertion, is every number derived from a run.

## 5. Handoffs
17. **Everything through git.** Nothing reaches a seat from a chat, a scratchpad or a download; the repo is the handoff. Secrets only in gitignored files, never printed or committed.
18. **A module is not closed until its downstream handoff pack is delivered** (interfaces, events, product rules, fixtures, a paste-ready prompt), versioned, as a PR to the consuming repo. The pack carries the ratified canon behind every parameter it states, not only the parameter.
19. **No unattended loops.** A dispatched run finishes and reports; nothing re-dispatches itself.
20. **Status to the owner in one shape: done / running / your step.** Short turns; one thing per turn; never hold a turn waiting on a run.
21. **Before any push, run the secret scan in CI's exact form.** Run CI's own scan script, with CI's scanner version and flags (allow comments ignored, every ref walked), on a clone where the branch to be pushed is present as a ref. A PASS from a hand-written equivalent or a narrower commit range does not predict CI's PASS. A seat never writes a scanner allow comment. A hit before the push is fixed by committing the change again on a new branch name that never held the content (rule 23), never by rewriting a lane's tree; a hit already pushed goes to the owner (rule 23).
22. **Evidence logs record labels, commands, exit codes and digests.** No committed file (log, report or record) prints a value the scan reads (addresses, keys, URLs, tokens); it prints the value's digest or length instead. A raw value a reviewer needs goes in the hand-back message or an out-of-repo hand-off folder, never in a committed file.
23. **No agent rewrites a pushed branch, and no agent runs or hands the owner a force flag.** That covers `--force`, `--force-with-lease`, `-f`, `-D`, `rm -rf`, `--hard`, `clean -f` and any flag whose purpose is to override a tool's refusal. A removal goes through the tool's own path after a reversible clean-up (a stash, a plain `git worktree remove`, `branch -d`), and if the tool still refuses, the seat stops and reports the message. Before any delete runs or reaches the owner, its checks are run and shown with it: contents, age, open files, git registration, unique commits, dirty files, references from records. A destructive action the permission system refuses is never retried in any form; the refusal is the owner's decision standing in for the owner, and it goes to the owner with the checks. A correction to a pushed branch is a new commit. A superseding head goes to a new branch name, and the superseded branch is listed for the owner, who alone deletes or rewrites it. If history must lose content (a secret), that is the owner's action, and the secret is rotated regardless: a rewrite clears the scan, never the exposure, because the removed commit may stay readable by its SHA. (Owner rule, 2026-11, after force commands were handed to the owner twice in one day; it replaces the earlier owner-approved same-name force-with-lease.)

## 6. Lanes, gates and landings
24. **Lane capabilities are fixed facts, attached by the dispatcher, never recalled.** There are three lane types, and the dispatcher prepends the lane type's contract to every brief (`SEAT_OPERATIONS.md` §11 has the table). An **author lane** edits its allowed paths and runs offline builds, lint and non-fork tests; it has no network (loopback included), cannot write git metadata (the coordinator commits its work verbatim), cannot read system counters and may be denied temp files. A **run lane** executes the fork runs and captures an author lane wrote down (exact commands, environment, expected counts), behind the resource gate, and commits its evidence without rewrites. A **lens lane** is read-only: it reads, replays and returns a verdict with findings. A brief that asks a lane for what its type cannot do is a brief defect, caught before dispatch. (2026-11: author lanes tried the network, git writes and system counters; one item lost three runs and another two, and every lens reported it could not run the shell selftest.)
25. **A resource gate is a wrapper that refuses, never a paragraph in a brief.** Heavy tools (compiler, node, fork runs, large test suites) are reached only through a wrapper on the lane's `PATH` that blocks until the coordinator's published gate file reads OPEN, then takes a lock: one forge lane at a time, and all heavy processes counted together against one machine-wide cap. The gate reads memory pressure as well as disk, because disk alone does not see one compiler process at eight gigabytes; it opens on any one of swap used under a floor, swap free over a floor, or nothing heavy running with free RAM over a floor, since a lone "swap free" test waits forever on a system that shrinks swap as use falls. A lane that cannot read the gate prints a distinct line and stops; a denied probe is never read as open or as blocked. (2026-10: a kernel panic under five seats; 2026-11: a memory gate written as brief prose was run straight through, and a lane that wrote its own reader for the gate file mis-parsed it and waited on an open gate; lanes call the coordinator's one reader.)
26. **Evidence from a run that broke a stated gate is invalid, whatever its content.** It is re-run inside the gate, never kept because it passed; a gate that evidence may ignore when convenient is not a gate. (2026-11: a capture that ran through the memory gate was rejected.)
27. **Space is recovered from a fixed list of the project's own paths, in a fixed order, and nothing else is surveyed.** The list names the project's registered worktrees and their build output, the seats' scratch of closed rounds and the tool sandboxes, and it names the protected paths (the RPC cache, archives, rescue copies, anything a live lane references), which are never touched. The order: the owner quits the large holders (a browser, a container runtime); finished lens worktrees, each through a checks script (unique commits, dirty files, holders, open panes) and the owner's yes per tree, removed with a plain `git worktree remove`; sparse checkouts; the project's own scratch after a delete check. Never a size scan over the home directory or system folders: the biggest things there include the owner's personal files and the most valuable live data. (2026-11, after repeated surveys of personal files.)
28. **Check a brief by script before spending a lens on it, and apply a lens's exact rewrites verbatim.** A brief lint resolves every `path:line` and `commit:path` citation at the named commit, checks every named tool flag against that tool's `--help`, and requires the allowed paths, the pass check and the final-line format. It fails a brief that quotes a standing rule it cannot resolve to a ruling or the owner's words (mark it `[ASSUMPTION]` and check it first), or that states an expected gate result nobody ran on that exact state. A lens reads only a brief that passes. When a lens returns exact rewrites, the coordinator applies them verbatim and dispatches; it does not spend another lens round re-reading its own copy of them. (2026-11: briefs took two or three lens rounds each, mostly on wrong citations and infeasible steps a script could have caught.)
29. **A brief that implements a ruling is counted against the ruling, never against itself.** Before dispatch a non-author reads the brief against the ruling's own text and returns a count: obligations in the source, obligations in the brief, and a source line for each. A mismatch fixes the brief, not the build. Every scope-check PASS names the binding source line and the count derived from it, and a reported "N bullets" is re-derived from the source before it is used. (2026-11: a brief carried seven of a ruling's twenty-three required rows, and the scope check compared the build with the brief.)
30. **One schema per cross-lane artifact, owned by the coordinator, written before the lanes that implement it.** When several lanes produce or consume one artifact (a handoff file, an acceptance index), the coordinator commits its contract first: one strict field set with no aliases, the digest formats, the consumer obligations, and one generated example that every lane validates against. No lane invents a shape, and a lane whose coordinator-owned input is missing stops with a line naming that input and never substitutes its own. (2026-11: a consumer lane was built to a different shape from the one its producer emitted, and had to change.)
31. **Rehearse before an evidence run.** Before any stop-on-first-failure evidence run (a capture, a gate wave, a replay) of harness code that has not yet met the full corpus, run a non-evidence rehearsal in collect-all mode over every arm, negative control and stop point the evidence run will reach; fix every gap in one batch, confirm, then run. Every confirm brief for a harness change also asks what else reads or depends on what the change moves (paths, profiles, environment, outputs). (2026-10: three evidence runs each stopped on a different harness gap, about four and a half hours lost.)
32. **Seats run the real check locally before a final line and before a push.** A local mirror runs every CI step that needs no fork (lint, the size gate, the census selftest, the document checks) on the tree, through the same scripts CI calls. Author lanes run it before their final line; the coordinator runs it before any push. (2026-11: a lint failure was first visible forty minutes into CI.)
33. **Wait on a process, and accept only a final line that carries a real commit.** A watcher waits on the lane's process id. When it exits, the coordinator reads its whole output and accepts only a final line in the brief's format whose commit resolves in the repository; it never matches text the brief itself contains, because a lane that echoes its brief echoes the template. Lane state lives in one registry file that survives a coordinator restart, never only in a session's watchers. (2026-11: five false trips on echoed template text; 2026-10: a danger line missed by reading only the last two lines of a watcher's output.)
34. **A landing is accepted only by a mechanical check plus a non-author lens.** By script: the commit the final line names is an ancestor of HEAD; the pushed head, if any, is an ancestor of HEAD (nothing was rewritten); the tree is clean; and the coordinator re-runs the brief's declared selftest itself. Then a non-author lens reads the landing. In a lane tree there is no reset, amend or rebase: a correction is a new commit, the final line prints once, after the last commit, and names the implementation commit, and nothing is committed after it except an evidence-only record of it. (2026-11: two lanes reset and recommitted after their final lines, which orphaned the pushed commits and stopped both output lenses on a head mismatch.)
35. **Run tooling has a stated bar and trust boundary, written before the first attack.** For tools that run evidence and keep records (recorders, runners, wrappers), the bar is: never stop or abandon a healthy run; never record a pass that was not one; make every check a ruling requires at the moment it requires it. What is not defended (another process on the machine changing files, a failing disk) is a one-line disclosed limit. A gap under the second item is fixed in code, never closed with brief text. After two rounds on the same small artifact, bring the owner the cut-down, not round three; every status says whether the item bears on contract security. This never lowers the bar on contracts, money paths, drivers that send, or the tier gate (rule 1). (2026-11: five attack rounds on a two-hundred-line recorder, with the deploy waiting.)
36. **A one-way door is flagged the moment it is found, and nothing deploys without the owner's word.** Every effect is named one-way (immutable bytecode, custody, launch terms, anything on chain) or two-way (signing rules, run books, alarms). A one-way effect goes to the owner as its own headline, before or with the recommendation, never as a footnote; a recommendation is checked against the live product plans first, and a fix that narrows a product path comes with the narrower fix that keeps the path open. No seat, executor or lane broadcasts to a live chain or runs a deploy: fork rehearsals only. A closed milestone, a green gate or a ratified ruling never implies the deploy; plans write the last step as "deploy, on the owner's go". (2026-10)
37. **A finding against a closed module leads with accept-and-disclose.** Reopening restarts the module's plan rows, census, evidence and audit scope. For a finding that moves no funds (a revert the caller pays for and retries, a checklist-literal duplicate check), the record states what fails, how often, that no funds move, and the off-chain mitigations, and the owner's default is to accept and disclose. A source change is raised, flagged as a reopen, only for loss of funds, a locked state, a blocked core flow, or a frequent failure on a default wallet path. (2026-10)
38. **Every lesson is filed with the layer that owns it and the artifact that enforces it.** The layer is harness, loop or graph; the artifact is a script, a wrapper, a CI step, a schema or a fixture, and a memory or brief line only points at it. A lesson that stays prose is marked `ADVICE` so it shows as debt. The scripts behind rules 1, 24, 25, 28, 32 and 34 (the tier gate, the dispatcher's lane contract, the gate wrapper, the brief lint, the local CI mirror and the land check) are each carried by the project; until a project has one, that rule is `ADVICE` in its ledger. (2026-11: of one night's lessons, the two that became structure held, and the gate kept as prose was run through.)
39. **Ask the other coordinator before answering the owner about its queue.** A question that depends on another coordinator's seats, queue or accounts gets one message to that coordinator first, and the answer comes from its reply, never from an assumption. (2026-11: an answer assumed the other side's work was serial; it had three parallel items ready.)

## 7. Six learnings from the hardest week
Read a ruling for its purpose and ask before building · re-running beats proving · freeze the producer chain before the first capture · name the evidence producer path · the independent closer is never waived, and two HOLDs means stop · spend is orchestration volume.
