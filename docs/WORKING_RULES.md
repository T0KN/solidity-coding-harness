# Working rules — how a coordinator, a builder and the lenses work together

These operating rules accompany `SOLIDITY_VERIFICATION_HARNESS.md`. The harness states what must be proven; this file states how the seats work. They bind every project created from this template. Copy them into the project's `CLAUDE.md` or link this file from it.

## The ladder
- **Harness:** what an agent can do (its tools, its sandbox, the wrappers that refuse).
- **Loop:** what is true (checks that can fail, run by script, before a lens is spent).
- **Graph:** what happens next and who decides (lanes, merge tiers, the owner's gates).
Every rule below sits on one layer, and a lesson is filed on the layer that owns it (rule 38).

## 1. Merges and PRs
1. **Merges are tiered by what a mistake costs to undo.** This owner decision, adopted 2026-11, replaces "no agent merges a PR, ever". The highest applicable reservation controls; builders, checkers and lanes never merge.
   - **Tier 1, integration only:** the coordinator may merge lens-accepted changes that touch no contract source into the INTEGRATION branch, never into `main`.
   - **Tier 2, owner:** `main`, gate files and repository settings stay the owner's.
   - **Tier 3, owner after the security gate:** contract source, deploys and multisig writes stay the owner's after the security gate.
   - **A tier is priced by what the change can reach after it lands.** Landing on a branch and promotion to anything a user or a chain can see (a live site, a deploy, a multisig write) are separate gates, and promotion is always the higher tier: a harmless-looking path still reaches users once it is promoted.

   Every tier gate has these properties, each for its reason. (2026-11: the first tier script merged a change before a non-author had reviewed the gate. The coordinator's report recorded nine holes across three versions. A later lens record executed 100 probes. A second run classified that record and inspected source, identifying 20 root causes: 16 classification causes and four additional defects. It also checked twelve historical regression categories, finding one incompletely closed, and rejected extending the deny-list design.)
   - a. **No gate is relied on before a non-author lens has read it.** A tier gate is itself a consequence path.
   - b. **The gate classifies complete, validated base and head objects, including added, removed and moved content, never a model's label.** Any acquisition, parse or read failure fails closed.
   - c. **Renames and deletions are judged on both the old and the new path.** Otherwise a move launders an owner-tier file into a tier-1 folder.
   - d. **Agent instruction files, CI files, the gate's implementation and its policy and trust inputs are always the owner's tier.** Policy and trust inputs include configuration, allow-lists, manifests and checksum pins. Files being classified do not become owner-tier merely because the gate reads them. A change to the gate cannot authorize itself.
   - e. **The gate executes a verified release that the merging seat and reviewed change cannot modify.** The protected release includes the launcher, engine, helper, parser and policy. Its dependencies do not come from the reviewed checkout. Versioned source is permitted; execution uses the protected installed release.
   - f. **Content checks parse both complete versions and preserve semantic distinctions.** Compare runtime dependencies, including type-only versus executable imports, resolved symbols, bindings and effect-relevant execution context. Preserve literal values and significant token boundaries. Counts, module prefixes, whitespace-normalized statements and added-line patterns cannot establish harmlessness. An unproved case goes to the owner.
   - g. **The merge is pinned to the exact head the gate judged** (the host's match-head option) **and needs a recorded non-author PASS on that same head and a clean merge state.** A push after the verdict cannot ride through. Classification and lens acceptance bind the repository, PR, full head SHA, base branch and full base SHA, merge base, integration tree and policy version. The merge mechanism must enforce those bindings against the current integration result atomically with integration. A separate client-side CLEAN read or another head/base read does not close that race. A changed binding requires fresh checks and acceptance.
   - h. **The gate accepts only an authenticated verdict that the merging identity cannot create or alter.** Validate a structured exact PASS, the checker identity, repository and PR, full head SHA, base and integration identities, and policy version. The required host check or attestation must be bound to its authorized issuer. The merging seat must have no access to the issuer's credential or signing service. A lens session record and its digest are audit evidence only; they do not substitute for independent authorization. If that boundary is unavailable, the coordinator does not merge.
   - i. **A local text-matching hook is not the wall.** It cannot see a merge performed inside a script. Host enforcement is required and must be verified for the configured identities, protected branches, owner-tier paths and independent lens issuer; README's day-one tests define the checks. The owner's guard hook is defence in depth, and it names the one permitted merge path by absolute path and checksum, an exception the owner writes.
   - j. **One implementation, with each project's path lists as data.** Two diverging tier scripts is the failure. Its planned home is `tools/tier/` in this repository (the engine, a per-project data file, content screens keyed by language), to be added by a separate PR after both lenses; until it lands, each project's gate meets a-i and k-m. Earlier `pr-tier.py`, `pr-tier-imports.cjs` and `merge-tier1.sh` prototypes are incident evidence, not an accepted reference implementation; reuse only properties that have been independently verified.
   - k. **Inertness is established by an allow-list and a non-consumption contract, never by a directory name.** An inert artifact is an approved regular, non-executable file that the application, build, CI and tooling cannot execute or interpret as active configuration. Scripts, queries, executable tests and stylesheets receive no inert exemption from their location. Source-free contract tooling and tests remain eligible for D1's integration-only route when no owner reservation applies. Automatic presentation-only classification requires a conservative language-aware verifier; unknown classifications go to the owner.
   - l. **The gate judges validated git objects, and any failure to obtain them is an error, never a pass.** Paths are canonical (no dot segments), and each file's object type and mode are established, so a symlink, a submodule link or an executable bit is seen; the changed-file list is unique, schema-checked, complete and bound to the judged head and base; an API patch, whether present, empty or absent, is not completeness evidence; derive the comparison from validated Git objects. An empty textual diff is acceptable only when blob identities and object metadata establish what changed. Approved binary artifacts are checked from their objects and metadata. A helper's output is ignored when its exit is non-zero; a failed fetch or merge-base stops the gate for every class of change. The base as well as the head is pinned at merge time.
   - m. **The release and its trust anchors are controlled by a different trusted principal.** Protect the launcher externally, before it executes. Validate the exact expected manifest membership and every digest, rejecting duplicate entries, missing members and unexpected paths. Execute the verified artifacts without a writable replacement path between verification and use. Policy data is owner-controlled, schema-validated, versioned and included in the attestation; it cannot weaken object, provenance or approval requirements.
2. **A PR opens only after its second lens has passed.** The PR body carries the verdict line: who reviewed, what they found, what was folded. CI green is never the review.
3. **One PR per real change; batch the rest.** Records, reports and hygiene changes accumulate on a staging branch (`docs/next`) and land as one PR.

## 2. Seats
4. **Author ≠ checker.** No seat clears its own work. A builder never approves its own PR; a checker never checks work its own model wrote; a top-severity oracle's lens differs from the builder's.
5. **Fresh thread per builder task; one task per thread.** A mid-task note goes into the live thread through a note script; a new task always respawns. Dispatch through a script that guards against the tool's own dialogs (updates, rate-limit model switches, slow-response menus): a bare Enter has switched models before.
6. **Briefs state reading scope** as exact files and line ranges, never "read in full"; they name the prior report if one exists; they require early checkpoints: commits for git-capable lanes, saved artifacts for author lanes, real exit codes and log paths in the hand-back. Files stay under 800 lines; a seat that reads a 2,000-line file whole dies with nothing committed.
7. **Non-interactive lanes use owner-authorized capability profiles.** Headless author, run and lens lanes follow `SEAT_OPERATIONS.md` §11; interactive builders follow its approval relay. Non-interactive refusal is not auto-approval. Model selection follows rule 10, and verification is never assigned to a cheaper model to save usage.

## 3. Discipline
8. **Primary-source discipline.** No claim about an external system without an in-context citation (a doc line, `file:line`, a decoded transaction, an RPC read); otherwise write "UNVERIFIED — not checked". "Probably/should/presumably" are banned as substitutes for looking. Equivalence and absence claims need end-to-end verification, never inference from silence. On pushback, re-read the source first. Tag material claims `[verified: <cite>]` or `[UNVERIFIED]`.
9. **Verify the claim, not its neighbour.** Reading the arithmetic at one line is not reading the guard on its input at another. Bind each proof to the exact property at its exact strength.
10. **Consequence decides the model, for authorship as well as review.** Anything that moves or gates money, authenticates, or protects data gets the strongest model for review, an adversarial second lens from a different model family, a real-world test where one exists (a live-state fork beats a mock; a differential against the live reference beats both), and never self-clearance. Complex tooling (drivers, runners, gate scripts) is a consequence path for its author: the strongest available author writes it, and fast models keep bounded edits and reading lanes (2026-11: a deploy-ceremony driver written by the fastest model came back from its lens with fifteen findings). Work whose error is self-evident and cheap to redo can use cheaper models.
11. **Nothing ratified is re-decided by an executing seat.** If something looks like a product or design call, it is written as a question for the owner to take to the deciding gate, never as a recommendation in a record. Every parameter in a record cites the ruling that set it.
12. **Test against the live reference whenever one exists.** A forked contract carries a live-matrix differential against the original on a pinned fork of mainnet; every difference maps to a named, priced register entry or blocks close-out; the run re-executes at every checkpoint close and every fee-path change, with its run id cited.

## 4. Machinery and spend
13. **New machinery gets two questions before it is built:** is this a rabbit hole, and does it bring us closer to shipping? Prefer re-running an existing check over building a new one. Two HOLDs on the same artifact for new shapes means stop and re-open the design with the owner, never a third round.
14. **Spend is orchestration volume, and the control is planning before dispatch, never a cap.** Task count and context size drive cost, not model choice; never downgrade a verifier to save tokens. Lenses read a verdict and a findings table, never a whole packet; fix loops batch fixes before re-checking. Before every dispatch the coordinator plans: the right seat and author for the item, the exact deliverable and its path, what already exists that must not be redone, and an estimate stated as a number, never as a limit. Never a spend cap, a hard stop on a number, or a floor or reserve held on a usage meter. A cap that stops a task with nothing committed wastes the spend it was meant to protect (2026-09). Each account's meter is read from the tool's own rate-limit record, never recalled (2026-11: two accounts' quotas were held backwards for hours). Never park work behind a reset while another account has room: every seat with work spends what is left, and a meter at zero waits for its reset while the other account carries on. `SEAT_OPERATIONS.md` §8 states the same budget rule.
15. **Tooling and CI changes are not "working" until their runtime capability is verified at source** (token scopes from the runner's permissions log, tools present on the runner), and their acceptance control is a mechanism-specific log line, never an outcome a silent failure also produces.
16. **A passing gate proves coverage and binding, never truth.** After any gate goes green, adversarially audit the content: does every claim prove its label, does every citation resolve to the exact assertion, is every number derived from a run.

## 5. Handoffs
17. **Everything through git.** Nothing reaches a seat from a chat, a scratchpad or a download; the repo is the handoff. Secrets only in gitignored files, never printed or committed.
18. **A module is not closed until its downstream handoff pack is delivered** (interfaces, events, product rules, fixtures, a paste-ready prompt), versioned, as a PR to the consuming repo. The pack carries the ratified canon behind every parameter it states, not only the parameter.
19. **No unattended loops.** A dispatched run finishes and reports; nothing re-dispatches itself.
20. **Status to the owner in one shape: done / running / your step.** Short turns; one thing per turn; never hold a turn waiting on a run.
21. **Before any push, run the secret scan in CI's exact form.** Run CI's own scan script, with CI's scanner version and flags (allow comments ignored, every ref walked), on a clone where the branch to be pushed is present as a ref. A PASS from a hand-written equivalent or a narrower commit range does not predict CI's PASS. A seat never writes a scanner allow comment. For an unpublished hit, reconstruct the sanitized change from a verified clean base under a new branch name, without rewriting the lane's branch. Run CI's exact scan with the same ref scope CI will inspect; do not narrow that scope to obtain a PASS. A contaminated published ref, or any cleanup requiring a refused or forced operation, goes to the owner under rule 23. Rotate an exposed secret regardless.
22. **Evidence logs record labels, commands, exit codes and digests.** No committed file (log, report or record) prints a value the scan reads (addresses, keys, URLs, tokens); it prints the value's digest or length instead. A raw value a reviewer needs goes in the hand-back message or an out-of-repo hand-off folder, never in a committed file.
23. **No agent rewrites a pushed branch, and no agent runs or hands the owner a force flag.** That covers `--force`, `--force-with-lease`, `-f`, `-D`, `rm -rf`, `--hard`, `clean -f` and any flag whose purpose is to override a tool's refusal. A removal goes through the tool's own path after a reversible clean-up (a stash, a plain `git worktree remove`, `branch -d`), and if the tool still refuses, the seat stops and reports the message. Before any delete runs or reaches the owner, its checks are run and shown with it: contents, age, open files, git registration, unique commits, dirty files, references from records. A destructive action the permission system refuses is never retried in any form; the refusal is the owner's decision standing in for the owner, and it goes to the owner with the checks. A correction to a pushed branch is a new commit. A superseding head goes to a new branch name, and the superseded branch is listed for the owner, who alone deletes or rewrites it. If history must lose content (a secret), that is the owner's action, and the secret is rotated regardless: a rewrite clears the scan, never the exposure, because the removed commit may stay readable by its SHA. (Owner rule, 2026-11; it replaces the earlier owner-approved same-name rewrite exception.)

## 6. Lanes, gates and landings
24. **Lane capabilities are fixed facts, attached by the dispatcher, never recalled.** There are three lane types, and the dispatcher prepends the lane type's contract to every brief (`SEAT_OPERATIONS.md` §11 has the table). An **author lane** edits its allowed paths and runs offline builds, lint and non-fork tests; it has no network (loopback included), cannot write git metadata (the coordinator commits its work verbatim), cannot read system counters and may be denied temp files. A **run lane** executes the fork runs and captures an author lane wrote down (exact commands, environment, expected counts), behind the resource gate, and commits its evidence without rewrites. A **lens lane** is read-only: it reads, replays and returns a verdict with findings. A brief that asks a lane for what its type cannot do is a brief defect, caught before dispatch. (2026-11: author lanes tried the network, git writes and system counters; one item lost three runs and another two, and every lens reported it could not run the shell selftest.)
25. **A resource gate is a wrapper that refuses, never a paragraph in a brief.** Heavy tools (compiler, node, fork runs, large test suites) are reached only through a wrapper on the lane's `PATH` that blocks until the coordinator's published gate file reads OPEN, then takes a lock: one forge lane at a time, and all heavy processes counted together against one machine-wide cap. The gate reads memory pressure as well as disk, because disk alone does not see one compiler process at eight gigabytes; it opens on any one of swap used under a floor, swap free over a floor, or nothing heavy running with free RAM over a floor, since a lone "swap free" test waits forever on a system that shrinks swap as use falls. A lane that cannot read the gate prints a distinct line and stops; a denied probe is never read as open or as blocked. (2026-11: a memory gate stated only in a brief was bypassed.)
26. **Evidence from a run that broke a stated gate is invalid, whatever its content.** It is re-run inside the gate, never kept because it passed; a gate that evidence may ignore when convenient is not a gate. (2026-11: a capture that ran through the memory gate was rejected.)
27. **Space is recovered from a fixed list of the project's own paths, in a fixed order, and nothing else is surveyed.** The list names the project's registered worktrees and their build output, the seats' scratch of closed rounds and the tool sandboxes, and it names the protected paths (the RPC cache, archives, rescue copies, anything a live lane references), which are never touched. The order: the owner quits the large holders (a browser, a container runtime); finished lens worktrees, each through a checks script (unique commits, dirty files, holders, open panes) and the owner's yes per tree, removed with a plain `git worktree remove`; sparse checkouts; the project's own scratch after a delete check. Never a size scan over the home directory or system folders: the biggest things there include the owner's personal files and the most valuable live data.
28. **Check a brief by script before spending a lens on it, and apply a lens's exact rewrites verbatim.** A brief lint resolves every `path:line` and `commit:path` citation at the named commit, checks every named tool flag against that tool's `--help`, and requires the allowed paths, the pass check and the final-line format. It fails a brief that quotes a standing rule it cannot resolve to a ruling or the owner's words (mark it `[ASSUMPTION]` and check it first), or that states an expected gate result nobody ran on that exact state. A lens reads only a brief that passes. Corroborate each finding against its cited source, apply the accepted exact rewrite verbatim, and retain the required review roster for the revised artifact. (2026-11: briefs took two or three lens rounds each, mostly on wrong citations and infeasible steps a script could have caught.)
29. **A brief that implements a ruling is counted against the ruling, never against itself.** Before dispatch a non-author reads the brief against the ruling's own text and returns a count: obligations in the source, obligations in the brief, and a source line for each. A mismatch fixes the brief, not the build. Every scope-check PASS names the binding source line and the count derived from it, and a reported "N bullets" is re-derived from the source before it is used.
30. **One schema per cross-lane artifact, owned by the coordinator, written before the lanes that implement it.** When several lanes produce or consume one artifact (a handoff file, an acceptance index), the coordinator commits its contract first: one strict field set with no aliases, the digest formats, the consumer obligations, and one generated example that every lane validates against. No lane invents a shape, and a lane whose coordinator-owned input is missing stops with a line naming that input and never substitutes its own.
31. **Rehearse before an evidence run.** Before any stop-on-first-failure evidence run (a capture, a gate wave, a replay) of harness code that has not yet met the full corpus, run a non-evidence rehearsal in collect-all mode over every arm, negative control and stop point the evidence run will reach; fix every gap in one batch, confirm, then run. Every confirm brief for a harness change also asks what else reads or depends on what the change moves (paths, profiles, environment, outputs).
32. **Seats run the real check locally before a final line and before a push.** A local mirror runs every CI step that needs no fork (lint, the size gate, the census selftest, the document checks) on the tree, through the same scripts CI calls. Author lanes run it before their final line; the coordinator runs it before any push. (2026-11: a lint failure was first visible forty minutes into CI.)
33. **Wait on the lane's process and validate its lane-specific final record.** Read the whole output after exit. An author lane reports its task identity, base commit, changed-file manifest, message-file path and check results; it does not claim an implementation commit. A git-capable run lane names its evidence commit. A lens names the exact reviewed commit and verdict. Match the registered task and record schema, never echoed template text. Persist lane state in the registry. (2026-11: five false trips on echoed template text.)
34. **A landing requires the mechanical check and a non-author lens.** The coordinator commits an author lane's allowed files verbatim with its message file, then writes the commit-bearing landing record. The land check verifies the implementation commit and any previously pushed head are ancestors of HEAD, verifies a clean tree and re-runs the declared selftest. The non-author lens reviews the resulting commit. No lane resets, amends or rebases; corrections are new commits or new author tasks. A lane prints its final record once. Only an evidence record may follow a completed implementation record without changing the implementation. (2026-11: two lanes reset and recommitted after their final lines, which orphaned the pushed commits and stopped both output lenses on a head mismatch.)
35. **Run tooling has a stated bar and trust boundary, written before the first attack.** For tools that run evidence and keep records (recorders, runners, wrappers), the bar is: never stop or abandon a healthy run; never record a pass that was not one; make every check a ruling requires at the moment it requires it. What is not defended (another process on the machine changing files, a failing disk) is a one-line disclosed limit. A gap under the second item is fixed in code, never closed with brief text. After two rounds on the same small artifact, bring the owner the cut-down, not round three; every status says whether the item bears on contract security. This never lowers the bar on contracts, money paths, drivers that send, or the tier gate (rule 1).
36. **A one-way door is flagged the moment it is found, and nothing deploys without the owner's word.** Every effect is named one-way (immutable bytecode, custody, launch terms, anything on chain) or two-way (signing rules, run books, alarms). A one-way effect goes to the owner as its own headline, before or with the recommendation, never as a footnote; a recommendation is checked against the live product plans first, and a fix that narrows a product path comes with the narrower fix that keeps the path open. No seat, executor or lane broadcasts to a live chain or runs a deploy: fork rehearsals only. A closed milestone, a green gate or a ratified ruling never implies the deploy; plans write the last step as "deploy, on the owner's go". (2026-10)
37. **A finding against a closed module leads with accept-and-disclose.** Reopening restarts the module's plan rows, census, evidence and audit scope. For a finding that moves no funds (a revert the caller pays for and retries, a checklist-literal duplicate check), the record states what fails, how often, that no funds move, and the off-chain mitigations, and the owner's default is to accept and disclose. A source change is raised, flagged as a reopen, only for loss of funds, a locked state, a blocked core flow, or a frequent failure on a default wallet path. (2026-10)
38. **Every lesson is filed with the layer that owns it and the artifact that enforces it.** The layer is harness, loop or graph; the artifact is a script, a wrapper, a CI step, a schema or a fixture, and a memory or brief line only points at it. A lesson that stays prose is marked `ADVICE` so it shows as debt. This template supplies the checkpoint-census implementation. Project-specific enforcement for rules 1, 5, 21, 24, 25, 27, 28, 32, 33 and 34 is not supplied here. Record each required script, wrapper, watcher and host configuration as implemented and verified, or `ADVICE`, in the project ledger. Record the schemas, rehearsal support and verification controls required by rules 30-31 and tenets 12-20 separately. `ADVICE` describes missing enforcement; it does not suspend an owner reservation or authorize a merge through a missing gate. (2026-11: two lessons became a gate-publisher file and a process-id waiter; a prose-only memory gate was bypassed.)
39. **Ask the other coordinator before answering the owner about its queue.** A question that depends on another coordinator's seats, queue or accounts gets one message to that coordinator first, and the answer comes from its reply, never from an assumption.

## 7. Six learnings from the hardest week
Read a ruling for its purpose and ask before building · re-running beats proving · freeze the producer chain before the first capture · name the evidence producer path · the independent closer is never waived, and two HOLDs means stop · spend is orchestration volume.
